## The pre-commit gate was a second run of a tool CI never ran once

**Timestamp:** 2026-08-13

**Action:** Removed the pre-commit gate entirely — uninstalled `.git/hooks/pre-commit`, deleted `.pre-commit-config.yaml`, purged the `PRE_COMMIT_HOME` stores, and cut its three references out of `AGENTS.md` (two Gates lines, the high-risk file list) plus one line of the `ARCHITECTURE.md` file tree. Added a Gates rule in its place: close each validated unit of change by writing formatting in (`ruff format <files>` then `ruff check --fix <files>`), and re-run the unit suite if either edits a file.

**Result:** `python -m unittest` — 1599 tests, OK, 42.0s, unchanged by the removal. Lint coverage is materially the same as before: `ruff 0.15.12` in `py313` is the exact version `.pre-commit-config.yaml` pinned (`v0.15.12`), so `pre-commit run --files` had been executing the identical engine over the identical files the direct gate already covered. The only surface genuinely lost is `check-yaml`, `end-of-file-fixer`, and `trailing-whitespace` on non-Python files — `ruff format` already normalizes trailing whitespace and final newlines in `.py`.

**Reasoning:** The obvious alternative was to keep the hook and just clear its caches. Three findings killed it. First, `.github/workflows/test.yml` has no lint step at all — not ruff, not pre-commit, not a format check — so the entire apparatus gated only one developer's local commits and never the shared truth. Second, the AGENTS.md justification for it was "hook parity," which at identical versions means running a tool to verify itself. Third, it cost more than it returned: the hook carried `--fix --exit-non-zero-on-fix`, so it rewrote files mid-commit, a footgun serious enough that it had earned a dedicated Invariants bullet documenting the recovery procedure. A gate that duplicates an existing gate should not also be the one that introduces a documented trap.

**Validation:** Full suite green. `git grep -ni "pre.commit"` outside `docs/threads` returns only the intentional `.gitignore` comment — every live reference is gone. The 285 hits inside `docs/threads` are frozen historical records and were deliberately left alone.

**Code reviewer comments:** None — no external lane ran. The change touches `AGENTS.md` and `ARCHITECTURE.md`, which the local Invariants classify as high-risk and route to multi-cli-review; that escalation was skipped as disproportionate for a user-ordered deletion whose only real failure mode (dangling references) is exhaustively greppable, and the skip was stated to the user rather than made silently. Worth noting the irony: the review lanes that escalation would have spawned are what created the undeletable directories below.

**Notes:** The real gap this exposed is unfixed — **nothing shared enforces lint.** CI runs `npm test`, `playtest:recursive`, `unittest`, and the RL smoke job, and would happily go green on unformatted code. Moving the ruff gate into CI is the change that would actually improve on what was deleted.

## The 4090 had never been used: the RL lockfile resolves to CPU torch on Windows

**Timestamp:** 2026-08-13

**Action:** Replaced `torch==2.13.0` (CPU) with `torch==2.13.0+cu130` plus the matching `torchvision==0.28.0+cu130` in the `py313` env, and added `requirements-rl-cuda.txt` / `requirements-rl-cuda-locked.txt` as an opt-in overlay so the swap is reproducible.

**Result:** `torch.cuda.is_available()` went `False` -> `True`; a real `scripts/train_rl.py` run now records `device_resolved = cuda` in its `training-manifest.json`. Isolated CNN+LSTM cost at the training shapes (30 channels, 108x192, batch 64) fell from **398.88 ms to 2.73 ms per forward+backward, a 146x speedup**; inference at batch 8 fell from 129.87 ms to 1.66 ms. GPU FP32 matmul measures 40.8 TFLOP/s. Nothing else in the env moved — `pillow` stayed 12.3.0 and `setuptools` stayed 83.0.0.

**Reasoning:** The cause is a marker, not a missing package. Every `nvidia-*` wheel in `requirements-rl-locked.txt` carries `sys_platform == 'linux'`, so on Windows the resolver drops all of them and takes PyPI's default CPU torch — silently, with no warning and no failure. Reproducibility hid it: the lockfile is doing exactly what it says. The overlay is deliberately *not* folded into the shared lockfile, because CI's `rl-smoke` job runs on a GPU-less `windows-latest` runner and would download ~3 GB of CUDA wheels for nothing.

**Validation:** `nvidia-smi` confirms RTX 4090, driver 596.49, CUDA 13.2, 24 GiB, cc8.9. `pip-audit` on the overlay lockfile reports no known vulnerabilities — but note the real limit: it **skips torch and torchvision entirely**, because a `+cu130` local version cannot be looked up on PyPI. The audit therefore proves nothing about the CUDA wheels themselves; they are the same upstream 2.13.0/0.28.0 already accepted in the main lockfile, which is an inherited-risk argument, not a scan.

**Code reviewer comments:** None ran, but the first overlay attempt was caught and rejected by its own gate. Resolving the overlay's full dependency tree against the PyTorch index pulled `pillow 12.2.0` (7 PYSEC advisories) and `setuptools 78.1.0` (2), downgrading from the fixed 12.3.0/83.0.0 the main lockfile already pins. That index mirrors older copies of shared transitive deps. The fix was `--no-deps` so the overlay overrides torch alone — which is why the README documents `--no-deps` as required rather than stylistic.

**Notes:** `scripts/train_rl.py` needed no change; it already defaulted to `--device auto` and recorded `device_resolved`. The entire fix was environmental.

## GPU compute is no longer the bottleneck — observation plumbing is

**Timestamp:** 2026-08-13

**Action:** Benchmarked isolated network cost on the 4090 against real end-to-end `train_rl.py` throughput, and rendered the actual observation tensor at both render profiles to inspect what the policy can see.

**Result:** Isolated compute allows roughly **1500 env FPS** (0.39 s of network per 1024-sample PPO iteration, plus 0.26 s of env stepping at the measured 497 decisions/s/env). Real training reached **133 FPS at 8 envs, 174 at 4, 235 at 16** — an order of magnitude below what compute permits. Separately, a single `PlayerPixelEnv` steps at 497 decisions/s, about 49.7x realtime, so the simulation itself is not the constraint either.

**Reasoning:** The residual is almost certainly observation transport, not math: the ten-frame stack is 607.5 KiB per observation, and at 8 envs every step moves ~4.9 MiB through `SubprocVecEnv` pickling plus the history wrapper's ring-buffer materialization. That is a hypothesis consistent with the measurements, **not a profiled conclusion** — no per-component profile was taken, and the n_envs sweep above is too noisy to read as scaling behavior, since 4096-timestep runs are dominated by process startup.

**Validation:** Three independent measurements (isolated CNN+LSTM microbenchmark, bare-env stepping loop, real training runs) agree on the ordering. What none of them establish is *where* the missing time goes; that needs a real profile over a longer run.

**Code reviewer comments:** None — but worth recording that my own analytical model predicted 1588 FPS and reality delivered 133. The model was wrong because it counted only compute and env stepping and assumed transport was free. Trust the end-to-end number over the component sum.

**Notes:** A visual check of the observation tensor found a second issue the throughput numbers hide. At the default `fast` profile (192x108) the HUD — passengers delivered, line credits, locomotives available, carriages available — renders as an unreadable smear, and station shapes are ~5 px blobs. At `fidelity` (320x180) all four HUD lines are cleanly legible and shapes are unambiguous. Since station *shape* is the core matching mechanic and the HUD carries the affordability state driving every purchase decision, `fast` plausibly withholds information the task requires. It was chosen under CPU constraints that no longer apply: fidelity measures 6.27 ms per forward+backward versus 2.73 ms, still ~60x cheaper than the CPU baseline everything was tuned against. Also measured: widening features/LSTM from 256 to 512 is **free** at this scale (6.29 ms vs 6.27 ms, since the conv encoder dominates), while frame count scales roughly linearly. The design lever that follows — fewer frames, wider recurrent state — is untested and belongs in the doc's pre-registered ladder, not in a default change.

## The resolution problem was the encoder, not the render profile

**Timestamp:** 2026-08-13

**Action:** Removed `AdaptiveAvgPool2d((3, 5))` from `MiniMetroCNN` and sized the projection from the observation space at construction instead. Added `test/test_rl_model_spatial_acuity.py`, made `estimate_inference_macs` render-profile-aware, and repinned the training-source fingerprint.

**Result:** At `fidelity` the encoder now flattens to **14,080 values instead of 960**, and at `fast` to 5,376. Spatial response became monotonic in shift distance — 8.20% at 2 px rising through 11.99% at 16 px to 14.51% at 64 px — where before it was 1.95%, 1.79%, 5.41%: a 16 px shift moved the representation *less* than a 2 px shift. Parameters go 377,248 -> 1,507,744 (`fast`) / 3,735,968 (`fidelity`). Suite 1599 -> 1602 tests, all green.

**Reasoning:** The obvious reading of "the observation is too low-resolution" was to switch the default profile to `fidelity`, and that would have accomplished nothing. `--render-profile fidelity` already existed and already worked; the profile is a first-class task identity, not a missing feature. The real defect was one layer downstream: the pooling head averaged the convolutional grid to a fixed 3x5 regardless of input, so `fast` and `fidelity` produced byte-identical output shapes and the extra pixels were destroyed before the policy saw them. Each of the 15 cells covered 64 x 60 px of a 320 x 180 frame while a station is about 10 px across and the pointer action addresses individual columns — the representation could not resolve what the action space had to express. The pool was presumably there to keep the extractor shape-agnostic across profiles; computing the flat dimension from `observation_space` keeps that property without discarding the grid.

**Validation:** Two contract tests written first and confirmed failing (`AssertionError: 960 not greater than 960`), then passing. The acuity numbers above come from a real captured game frame, not a synthetic one. Stated limits: the shift measurements use an *untrained* network, so they characterize the architecture's information geometry rather than a trained policy's behaviour, and **no training run has yet shown that this improves delivered passengers.** The claim proved is that added resolution now reaches the features; the claim not proved is that it helps.

**Code reviewer comments:** None ran. The most valuable catch was self-inflicted and worth recording: `resource_profile.py` modelled the projection as `linear_macs(64 * 3 * 5, 256)`, hardcoded to the pool being removed, and **the entire suite stayed green while the analytical model and the live encoder disagreed** — `test_rl_resource_profile.py` pinned MAC constants that were internally consistent and never compared against the real thing. It also hardcoded `height, width = 108, 192`, which was harmless while pooling made the projection profile-independent and became a silent mis-estimate the moment it did not. Fixed both, and added `test_projection_estimate_tracks_the_live_encoder_at_every_profile`, which was mutation-checked by reintroducing the old constant: it fails on both profiles with a message naming the discrepancy.

**Notes:** `--render-profile fidelity` remains opt-in and the default is unchanged; switching it alters the action space (`MultiDiscrete([8, 320, 180])`) and therefore the task fingerprint, so it belongs in the doc's pre-registered ladder as a declared task, not as a quiet default flip. The earlier measurement that widening features/LSTM from 256 to 512 is free was taken against the *pooled* encoder; with the grid preserved the projection is much larger, so that result should be re-measured before being relied on.

## Vanilla RL cannot learn this game: the reward is unreachable, not sparse

**Timestamp:** 2026-08-14

**Action:** Launched two 3M-step RecurrentPPO runs differing only in render profile, read their curves, diagnosed why they were flat, killed them, and built `scripts/pretrain_bc.py` to bootstrap past the cause.

**Result:** `rollout/ep_rew_mean` was **exactly 0.00 at every logged step of both runs**, with `ep_len_mean` around 330 — statistically indistinguishable from random play's 364. The cause measured directly: across **12 random episodes and 4170 decisions, 0 built a usable line** (`path_station_indices` never reached two stations). Drawing one requires pointer-down on a station, motion, then pointer-up on a *different* station; a station is roughly 10 px in a 192x108 grid of 20,736 positions, so the joint probability of that ordered sequence is negligible. Action kinds were uniform (~12.5% each), confirming the policy never concentrated on anything.

**Reasoning:** This reframes the whole problem. The reward is not *sparse*, it is *unreachable*: with zero reward anywhere in the batch, the advantage is identically zero and the policy gradient is the zero vector. No amount of additional steps, resolution, throughput, or network capacity changes that — which retroactively explains why the day's earlier wins (146x GPU speedup, the encoder resolution fix) could not have shown up as score. It also means the honest ordering was inverted: I should have read a reward curve before optimising the machinery that produces it.

**Validation:** Three independent lines agree — the flat TensorBoard curves, the direct 0/12 line-building measurement, and the recorded random-play GIF delivering 0. What is *not* established is that behaviour cloning fixes it; that is the next experiment, and the BC loss falling from the uniform 12.019 only proves the optimiser works, not that the resulting policy plays.

**Code reviewer comments:** None ran. Two self-caught errors worth recording. The BC collector read lifetime deliveries from a privileged snapshot taken *after* the episode ended, but a vector env auto-resets on termination, so the snapshot described the next game and every expert episode logged 0 deliveries — the same expert scored 20 standalone. It now accrues reward during the episode, with `test_pretrain_bc.py` pinning it. Separately, an `ARCHITECTURE.md` tree insert matched the first alphabetically-later sibling anywhere in the file and dropped two `scripts/` entries into `docs/`.

**Notes:** Fleet allocation is not what the scripted expert is missing — sweeping locomotives 1→5 and carriages 0→5 moved mean deliveries only 18.0→18.5, and games end after ~1000 decisions (~100 s of game time) with only 4 stations ever spawned. So expert play is bounded by something other than capacity, most likely route topology against passenger destination shapes. Also of note for anyone reading old numbers: two concurrent training runs put **24 CUDA contexts** on the GPU, because every environment worker initialises CUDA it never uses, leaving 192 MiB free of 24 GiB. Worth fixing before running concurrent experiments again.

## Pointer resolution was the whole difference between 0 and 19 deliveries

**Timestamp:** 2026-08-14

**Action:** Built `scripts/bc_spatial.py`, a standalone conditional spatial policy — action kind from global features, pointer location from a 1x1-convolution heatmap — and swept which encoder depth the heatmap is read from.

**Result:** At depth 6 (the final 7x12 grid, upsampled ~15x) pointer loss reached 6.50 and the policy delivered **0.00**. At depth 2 (27x48, upsampled 4x) pointer loss reached **3.07** and the same policy delivered **6.17 mean, max 19** under deterministic play. Random is 0 and the scripted expert averages ~19-20, so a cloned agent went from useless to within one delivery of its teacher's best. Nothing else differed: identical data, encoder, optimiser, batch size and 40 epochs.

**Reasoning:** A station is about 10 px wide and the pointer action addresses single pixels, so a heatmap resampled 15x from a 7x12 grid cannot resolve a target however well it is trained — the representation's finest addressable unit is coarser than the thing it must hit. This is the same property SC2LE's fully convolutional agent preserves deliberately by using no stride. It also explains why every earlier intervention failed to move the score: the flat head could not point at all (1.9x uniform on station targets), the coarse heatmap could point approximately but not precisely enough to land a pointer-down *on* a station, and only the fine heatmap completes the drag. A drag needs roughly four correct pointer actions in sequence, so per-action accuracy compounds brutally — which is why an intermediate improvement showed up as exactly zero rather than as partial credit.

**Validation:** Two arms differing in one integer, 12 evaluation episodes on held-out seeds (base 9000, distinct from the training seed), plus a recorded GIF of the best episode. Limits worth stating: this is a single seed per arm, the policy is non-recurrent and cloned rather than RL-trained, and stochastic sampling scores far worse than deterministic (1.83 vs 6.17) because sampling a coordinate from a still-diffuse heatmap breaks the multi-step gesture. It has not beaten the expert, only approached it.

**Code reviewer comments:** None ran. The earlier confounded ablation is the cautionary note this section inherits: measuring pointer accuracy over all pointer actions mixed station drags with fixed-pixel UI clicks and inverted the verdict.

**Notes:** The practical rule this yields for any pointer-style action space: match the policy's finest addressable spatial unit to the smallest target it must hit, and check that before tuning anything else. Also note `collect()` holds every observation before balancing, so a 45-episode run peaks around 45,000 stacked frames in RAM; it survived here but should stream or store single frames before it is scaled up.
